> **Platform:** HackTheBox | **Type:** Sherlock (DFIR) | **Difficulty:** Very Easy
> **Skills:** log analysis, brute force detection, MITRE ATT&CK mapping
> **Tools:** `7z`, `grep`, `sort`, `uniq`, `utmpdump`

Brutus. A Linux server. Two log files. One very unlucky root account.

This one is different from most HTB stuff you'll see. **Nobody is hacking anything.** The attack already happened, and our job is to read the evidence and work out what the attacker did. That's called **DFIR** (Digital Forensics and Incident Response), and a Sherlock is HTB's version of it.

No exploits. No shells. Just us, a terminal and a lot of `grep`.

## What even is this?

We get a zip with three files:

| File | What it is |
|------|-----------|
| `auth.log` | A plain text log of every authentication event on the server: logins, failed logins, `sudo` commands, new users. This is the main evidence. |
| `wtmp` | A **binary** log of every login and logout, with the user, the IP and the terminal used. You can't `cat` it, we'll need a tool. |
| `utmp.py` | A Python script that reads `wtmp`. We won't need it, `utmpdump` does the same job. |

The story in one line: someone **guessed the root password over SSH**, got in, **created a backdoor account** and used it to **download a script**. Let's prove it.

## Step 0: Getting the files out

Download the zip from the HTB page and extract it in WSL. The password for every Sherlock zip is `hacktheblue`.

I first tried the normal way and hit two walls:

- Windows threw `Error 0x80004005: Unspecified error` while extracting.
- `unzip` in WSL said `skipping: auth.log  unsupported compression method 99`.

**Method 99 means the zip uses AES encryption**, which plain `unzip` doesn't understand. `7z` does:

```bash
sudo apt install p7zip-full -y
7z x /mnt/c/Users/<you>/Downloads/Brutus.zip -phacktheblue -o$HOME/htb/brutus -aoa
```

- `7z x` extracts the archive.
- `-phacktheblue` is the password. **No space** after `-p`.
- `-o$HOME/htb/brutus` is the output folder. Again, no space after `-o`.
- `-aoa` overwrites files that already exist (`unzip` had already extracted `utmp.py`).

## Step 1: Who is the attacker? (Task 1)

A brute force attack means trying passwords again and again, so the log will be full of **failed logins from the same IP**. Let's count them:

```bash
grep -i "failed password" auth.log | grep -oE 'from [0-9]+\.[0-9]+\.[0-9]+\.[0-9]+' | sort | uniq -c
```

Piece by piece:

- `grep -i "failed password" auth.log` keeps only failed login lines (`-i` ignores upper/lower case).
- `grep -oE 'from [0-9]+\.[0-9]+\.[0-9]+\.[0-9]+'` prints **only** the matching part, which is the word `from` followed by an IP. `-o` = only matching part, `-E` = lets us use a pattern.
- `sort` puts identical IPs next to each other.
- `uniq -c` collapses the duplicates and puts a count in front.

One IP owns basically every failure: **`65.2.161.68`**. That's our attacker.

> **Mistake I made:** my first grep matched `ip-172-31-35-28` and I submitted it. Wrong. That's the **server's own hostname**, which sits at the start of *every* log line (`Mar 6 06:31:31 ip-172-31-35-28 sshd[...]`). It's the victim, not the attacker. The attacker's IP is the one after the word **`from`**.

## Step 2: Which account did they get into? (Task 2)

Failed attempts are boring. What we care about is the one that **worked**. Successful SSH logins are logged as `Accepted password`:

```bash
grep "Accepted password" auth.log | grep 65.2.161.68
```

```
Mar  6 06:31:40 ... sshd[2411]: Accepted password for root from 65.2.161.68 port 34782 ssh2
Mar  6 06:32:44 ... sshd[2491]: Accepted password for root from 65.2.161.68 port 53184 ssh2
Mar  6 06:37:34 ... sshd[2667]: Accepted password for cyberjunkie from 65.2.161.68 port 43260 ssh2
```

The attacker got in as **`root`**. The highest privilege account on a Linux box, and it fell to a password guess. Ouch.

Also notice the third line, a *different* user from the same IP. Keep that in mind.

## Step 3: When did they actually log in? (Task 3)

You'd think the `Accepted password` time is the answer. It isn't, and the task warns us: *the login time will be different than the authentication time*.

- **Authentication time** (`auth.log`): the moment the password was accepted.
- **Login time** (`wtmp`): the moment the terminal session was created.

They differ by about a second. To read `wtmp` we need `utmpdump`, which turns the binary into text:

```bash
TZ=UTC utmpdump wtmp | grep 65.2.161.68
```

- `utmpdump wtmp` converts the binary file to readable text.
- `TZ=UTC` sets the timezone for this one command to UTC. Without it, WSL shows **your local time** (IST for me) and the answer would be off by 5.5 hours. The task asks for UTC.
- `| grep 65.2.161.68` keeps only the attacker's lines.

Each line has the terminal (`pts/N`, meaning an interactive session), the user, the IP and the timestamp at the end.


## Step 4: Which session number? (Task 4)

Every SSH login gets a session number from `systemd-logind`, not `sshd`. That's why grepping for the IP never shows it. We search for `New session` instead:

```bash
grep "New session" auth.log
```

```
Mar  6 06:19:54 ... New session 6 of user root.
Mar  6 06:31:40 ... New session 34 of user root.
Mar  6 06:32:44 ... New session 37 of user root.
Mar  6 06:37:34 ... New session 49 of user cyberjunkie.
```

Match by **user and time**. The `wtmp` login came up with the root login at 06:32:44, so the attacker's session is **`37`**. Session 34 came right after the brute force, and session 6 is earlier, unrelated activity.

## Step 5: The backdoor account (Tasks 5 and 6)

Now what did they do inside? Let's look for new accounts:

```bash
grep -i "new" auth.log
```

```
Mar  6 06:34:18 ... groupadd[2586]: new group: name=cyberjunkie, GID=1002
Mar  6 06:34:18 ... useradd[2592]: new user: name=cyberjunkie, UID=1002, GID=1002, home=/home/cyberjunkie, shell=/bin/bash, from=/dev/pts/1
Mar  6 06:37:34 ... New session 49 of user cyberjunkie.
```

- `useradd` is the Linux command that creates a user. The attacker made **`cyberjunkie`** (Task 5).
- `groupadd` just before it is automatic, `useradd` makes a matching group.
- `from=/dev/pts/1` tells us the command was typed in an **interactive terminal**, so a human did it by hand.
- At 06:37:34 they log in as `cyberjunkie`, so the account really was used as a backdoor.

**Why make a new account?** Persistence. If the admin notices and changes the root password, the attacker still has a way in.

### MITRE ATT&CK, in plain words

[MITRE ATT&CK](https://attack.mitre.org) is a public catalogue of attacker behaviour. Every behaviour has an ID so defenders everywhere describe things the same way. It works in layers:

- **Tactic** = the goal. Here: **Persistence** (stay in).
- **Technique** = how. Here: **Create Account (T1136)**.
- **Sub-technique** = the specific flavour. Here: **Local Account (T1136.001)**, because the account was made on the machine itself, not in a domain or cloud service.

Answer for this task is **`T1136.001`**.

## Step 6: When did the first session end? (Task 7)

Sessions also get logged when they close. Let's read every session line:

```bash
grep -i "session" auth.log
```

`New session N` is a start. `Removed session N` (from `systemd-logind`) is the end. I already knew the session number from Step 4, so I scanned for that number and read the timestamp on its `Removed session` line.

## Step 7: What did they download? (Task 8)

The attacker used `cyberjunkie` and its `sudo` rights to run something as root. Every `sudo` command is logged with a `COMMAND=` field:

```bash
grep -i "sudo" auth.log
```

A line looks like this:

```
sudo: cyberjunkie : TTY=pts/1 ; PWD=/home/cyberjunkie ; USER=root ; COMMAND=/usr/bin/...
```

- `cyberjunkie` = who ran it.
- `USER=root` = it ran with root power.
- `COMMAND=` = exactly what was run.

Most lines are the attacker poking around. The one that matters uses `curl`, a tool that downloads files from a URL. 

**The attacker downloaded a script from the internet and ran it with root privileges on the server.** That URL is an **IOC** (Indicator of Compromise): a trace you'd block and hunt for on other machines.

## The full story

```
Brute force from 65.2.161.68
        ↓
Password guessed → SSH login as root
        ↓
Manual terminal session (wtmp)
        ↓
useradd → backdoor account "cyberjunkie"
        ↓
Login as cyberjunkie
        ↓
sudo curl → script downloaded with root privileges
```

## What did I actually learn?

- **Logs tell a story if you read them in order.** Every step above led to the next.
- **Different logs answer different questions.** `auth.log` shows attempts and commands, `wtmp` shows real sessions and times.
- **Read the fields, not just the lines.** My hostname mistake happened because I grepped a pattern without looking at what it matched.
- **Timezones bite.** Always check whether a tool shows UTC or local time.
- **MITRE ATT&CK** gives a shared name to what you found, which is what an incident report needs.

## How should this be fixed?

- **Disable root login over SSH** (`PermitRootLogin no`).
- **Use SSH keys, not passwords** (`PasswordAuthentication no`). You can't brute force a key.
- **Install `fail2ban`**, which bans an IP after too many failed logins. A wall of failures from one IP should never have been possible.
- **Alert on new user creation and unusual `sudo` use.** Someone should have been paged when `useradd` ran at 06:34.

## Final takeaway

Brutus didn't need a clever exploit. It needed a weak root password and nobody watching the logs. The attacker got in loudly, left fingerprints on every step, and `grep` was enough to catch all of it.
It's always the boring logs that tell on you.
