TimeKORP. A tiny PHP web app. A clock. One innocent-looking `format` parameter.

*What could possibly go wrong?*

Turns out, quite a lot.

This challenge is about **OS Command Injection** — getting a web application to stop doing what the developer intended and start doing what *you* tell it to do.

## What even is this?

TimeKORP lets you choose how the server displays the current time.

For example:

```text
?format=%H:%M:%S
```
Behind the scenes, the application takes that format and builds a Linux date command:

```bash
date '+<format>' 2>&1
```

Normally, that's perfectly fine.

Except our input is being placed directly inside a shell command.

And whenever you see user input going straight into a shell, there's one question worth asking:

*Can I make it do something other than what it was supposed to?*

## Step 1 — Finding the weakness

The important part of the application was the format parameter.

The application essentially does this:
```bash
date '+<user input>' 2>&1
```
The input isn't properly sanitized or validated.

So instead of giving it another time format, I tried to break out of the quotes.

## Step 2 — Breaking out of the command

The format is surrounded by single quotes:
```bash
date '+<format>' 2>&1
```
So the first thing we need is:

`'`

to close the existing quote.

Then we can use:

`;`

to start a new command.

Finally:

`#`

comments out the remaining part of the original command.

Putting everything together:

`';id #`

The server now ends up executing something conceptually similar to:
```bash
date '' ; id #'
```
The three important pieces:

`'` → closes the original quote
`;` → lets us start another command
`#` → comments out the rest

And just like that, the clock has developed a new career.

## Step 3 — Do we actually have command execution?

Time to test it.

I sent:
```text
?format=';id #
```
The response showed that the command was executed as the:

`www`

user.

So we had confirmed OS command injection.

No complicated exploit.

No reverse shell.

Just:

*Hey server, can you run id for me?*

And it did.

## Step 4 — Looking around

Now that arbitrary commands could be executed, I wanted to see what was sitting on the filesystem.

The obvious command:
```bash
ls -la /
```
had a small problem.

PHP's `exec()` returns the last line of command output. Since ls normally produces multiple lines, most of the output wasn't making it back to us.

So I flattened the output into a single line:
```bash
ls -la / | tr '\n' ';'
```
`tr` replaces every newline with `;`.

Instead of:
```bash
file1
file2
file3
```
we effectively get:
```bash
file1;file2;file3;
```
Much easier for exec() to return.

And there it was:
```bash
/flag
```
Well. That was convenient.

## Step 5 — Grab the flag

We knew exactly where the flag was.

So there was no reason to overcomplicate things.

Payload:

```text
';cat /flag #
```
Which makes the server execute:
```bash
cat /flag
```
And the flag appeared.

Flag. Done.

## What did I actually learn?

The important part of this challenge wasn't the payload.
It was understanding where the input goes.
The application trusted the format parameter and placed it directly into a shell command:
```bash
date '+<user input>' 2>&1
```
Because there was no proper validation, we could escape the intended command and execute our own commands.

The attack was basically:
```text
User input
    ↓
PHP application
    ↓
Shell command
    ↓
Command injection
    ↓
Arbitrary command execution
```

### How should this be fixed?

The safest option is to avoid shell execution with user-controlled input altogether.

If shell execution is absolutely necessary, the application should strictly whitelist the allowed time formats instead of accepting arbitrary input.

For example, only allowing known formats such as:
```text
%H:%M:%S
%Y-%m-%d
```
rather than letting the user provide anything they want.

## Final takeaway

TimeKORP wanted to tell me the time.

Instead, I convinced it to tell me who it was, show me its filesystem, and hand me the flag.

It's always the innocent-looking parameters.
